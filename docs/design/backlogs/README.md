# Design Backlogs

backlog는 아직 착수하지 않았거나 여러 작업으로 나눠야 하는 개선 과제를 주제별로 모아 둔다. 각 항목에는 무엇이
문제이고 어디까지 고치면 끝나는지 적어 두었다가, 착수할 때 spec(`docs/specs/`)이나 구현으로 넘긴다. backlog는
결정 기록이 아니다. 승인된 결정은 `docs/DECISIONS.md`에만 적는다.

`docs/TODO.md`는 제품 로드맵과 장기 후보를 관리한다. 이 폴더는 특정 작업이나 점검에서 나온 후속 과제를 관리한다.
같은 과제를 두 곳에 적지 않는다. 로드맵 단위로 커지면 `docs/TODO.md`로 옮기고 이곳 항목은 `retired`로 닫는다.

## 파일

```text
docs/design/backlogs/YYYY-MM-DD-<topic>-backlog.md
```

- 이름은 소문자 ASCII kebab-case로 쓰고, 본문이 주로 한국어면 끝에 `-ko`를 붙인다. 생성일은 바꾸지 않는다.
- 한 주제는 파일 하나로 관리한다. 같은 주제를 다시 점검하면 새 파일을 만들지 않고 기존 파일을 갱신한다.

## frontmatter

```yaml
---
type: design-backlog
id: INSTALL
status: proposed
priority: 중요
created: 2026-11-06
reviewed: 2026-11-06
base: main@9cf5e4d
---
```

- `id`: 문서 ID다. 대문자로 쓴다. 항목 ID는 문서 ID에 두 자리 번호를 붙여 만든다(`INSTALL` → `INSTALL-01`).
- `status`: 문서 상태다. 열린 항목 중 하나라도 `in-progress`이면 `in-progress`, 아니면 `proposed`다. 모든 항목이
  닫히면 `done`이다.
- `priority`: 열린 항목 중 가장 높은 우선순위다.
- `reviewed`: 문서 전체를 마지막으로 코드와 대조한 날이다. 대조한 적이 없으면 뺀다.
- `base`: 마지막으로 대조한 브랜치와 commit이다.

## 상태

문서와 항목이 같은 값을 쓴다.

- `proposed`: 문제와 방향을 기록했지만 착수 승인은 없다.
- `ready`: 범위, 선행 조건, 완료 조건이 정해져 착수할 수 있다.
- `in-progress`: 승인된 구현이나 spec 작업이 진행 중이다.
- `blocked`: 외부 결정이나 확인이 없어 진행할 수 없다.
- `done`: 완료 조건을 모두 충족했다.
- `retired`: 진행하지 않는다. 사유와 대체 문서를 남긴다.

## 우선순위

| 우선순위 | 뜻 | 착수 시점 |
| --- | --- | --- |
| 긴급 | Vault 파일 손상, 설치·업그레이드 실패, 색인이나 MCP가 복구 안내 없이 멈춤 | 다음 patch 릴리스 |
| 중요 | 체감 성능, 사용자를 잘못된 행동으로 이끄는 안내, 핵심 경로의 테스트 공백 | 다음 minor 릴리스 |
| 일반 | 조건이 좁은 결함, 안내 문구의 불일치, 구조 문제. spec이 필요할 수 있다 | 일정을 잡아 진행 |
| 권장 | 문서 정리, 테스트 보강, 중복 코드 정리 | 해당 코드를 고칠 때 함께 |

## 본문 구성

1. 목표와 범위. 범위 밖인 것도 적는다.
2. 한눈에 보기. 열린 항목의 ID, 제목, 우선순위, 상태, 선행 조건을 표 하나로 적는다. 항목을 옮기거나 닫으면 이
   표도 함께 고친다.
3. 이 문서만의 규칙. 이 README와 다른 규칙만 적는다. 없으면 섹션을 뺀다.
4. 점검 이력. 한 줄에 날짜, base commit, 범위, 결과, 실행하지 못한 것을 적는다.
5. 우선순위별 열린 항목. 섹션은 긴급, 중요, 일반, 권장 순서다. 항목이 없는 섹션은 뺀다.
6. 닫힌 항목 표. ID, 제목, 상태, 날짜, 근거(PR이나 retired 사유)를 적는다.
7. Open Decisions. 착수 전에 정해야 할 질문, 선택지, 권장안을 적는다.

## 항목 형식

```markdown
### INSTALL-02 문제를 한 문장으로 적는다
- [ ] proposed · 성능 · indexing · 확인 2026-11-06
- 문제: [확인] 코드나 측정에서 확인한 사실. [가정] 확인하지 못한 부분.
- 영향: 사용자가 겪는 결과.
- 방향: 고치는 방법.
- 완료: 완료 조건. 검증 방법을 겸한다.
- 선행: INSTALL-05, Open Decision 2
- 출처: 이 항목을 처음 찾은 PR, 리뷰, 측정
- 연결: spec 경로, 브랜치, PR
```

- 상태 줄은 상태, 관점, 대상 모듈, 마지막으로 코드를 확인한 날짜 순서다. `[확인]` 주장이 없으면 날짜를 뺀다.
- 주장 표시는 `[확인]`(코드나 측정으로 확인), `[결정]`(사람이 정함), `[가정]`(확인하지 못함), `[외부]`(다른
  사람이나 리뷰어의 주장)를 쓴다. `[가정]`과 `[외부]`는 착수 전에 다시 확인한다.
- `영향`은 문제가 사용자에게 어떻게 보이는지 한 문장으로 적는다. 우선순위를 정하는 근거다.
- `선행`이 없으면 줄을 뺀다. `연결`은 착수할 때 추가한다.
- 코드 위치는 줄 번호가 아니라 파일과 심볼 이름으로 적는다.

## 운영

- 항목 ID는 다시 쓰거나 번호를 새로 매기지 않는다. 우선순위가 바뀌면 항목을 다른 섹션으로 옮기고 ID는 유지한다.
- 항목을 고치는 PR이 backlog도 함께 고친다. 머지되는 PR에서 항목을 닫힌 항목 표로 옮긴다. 일부만 고쳤다면
  항목을 열어 두고 `문제`를 남은 부분으로 고친다.
- 닫힌 항목은 지우지 않는다. 고친 문제가 다시 생기면 같은 ID로 다시 연다.
- 다시 점검하면서 코드와 대조한 항목은 상태 줄의 확인 날짜를 갱신한다. 날짜가 오래된 항목은 아직 유효한지 모른다는
  뜻이다.
