# 드리밍 dry-run과 심은 오류 측정 (2026-11-19)

spec `docs/specs/2026-11-19-memory-dreaming/spec.md` §7, 구현 순서 8과 9.

## 요약

- 드리밍은 실제 세션 대기열에서 끝까지 돌았다. Vault와 Graph Home에는 아무것도 쓰지 않았다(dry-run).
- 교환 16개를 판단하는 데 51초, $0.40이 들었고 제안 1개가 나왔다.
- 심은 오류 시험은 20건(심은 오류 10, 대조군 10)에서 10개를 모두 찾았고 잘못 올린 것은 없다. 사례가 적고 실제보다 쉽다.
- 드리밍 전에 대기 교환으로 질문 26개를 써 두었다. 지금은 기억된 것 0, context pack이 찾은 것 0이다.
- 승인율과 승인 뒤 비교는 아직 값이 없다. 사람이 실제 제안을 해결해야 생긴다.
- 찾은 한계 둘:
  - 페이지를 뒤집는 교환이 검색 상위 5개에 없으면 그 페이지는 확인되지 않는다.
  - 판단이 건너뛰는 쪽으로 기울었을 수 있다. dry-run은 16개 중 1개를 골랐고, 질문을 쓴 에이전트는 139개 중 38개쯤에 남길 내용이 있다고 봤다.

## 방법

- 코드는 이 브랜치(`feat/jh/agent-memory-dream`)다.
- 실제 Graph Home과 실제 Vault를 읽기만 했다. `run_dream(..., manual=True, dry_run=True)`을 직접 불렀고, 설정 파일을 만들지 않으려고 묶음 한도만 코드에서 낮췄다.
- 판단은 로그인된 `claude -p --model claude-sonnet-5-5`다.
- 결과 1과 2는 프롬프트 `dream-1`로 쟀다. 그 뒤 검토에서 프롬프트를 `dream-2`로 고쳤고(페이지 확인 항목 설명, 주장 표가 없는 페이지의 교정 방법), 결과 3은 `dream-2`로 쟀다. 결과 1과 2는 다시 재지 않았다.
- 실행 전후로 `configs/dream.json`, `dream/`, `logs/dream-runs.jsonl`이 없는 것을 확인했다.
- 세션 내용은 이 보고서에 옮기지 않는다.

## 결과 1: 세션 교환 판단 (D2, `dream-1`)

| 값 | 결과 |
|---|---|
| 판단한 교환 | 16개 (묶음 8개씩 두 번) |
| 프롬프트 크기 | 74,031자, 81,731자 |
| 걸린 시간 | 50.8초 (후보와 비교 페이지 찾기 포함) |
| 비용 | $0.395 |
| `none` | 15 |
| 제안할 것 | 1 (`update_memory`) |
| 인용 확인에서 걸러진 것 | 0 |
| 잘못된 답 | 0 |

- 제안 1개는 이미 있는 결정 페이지에 내용을 덧붙이는 것이었다. 새 페이지를 만들지 않았다.
- 인용문은 사용자가 친 한국어 문장 그대로였고 오타도 그대로였다. 인용 확인을 통과했다.
- 덧붙일 글은 대상 페이지의 언어(영어)로 쓰였다. 프롬프트 규칙 3과 맞다.
- `none` 15개 가운데 놓친 것이 있는지는 확인하지 않았다. 아래 결과 4의 질문 세트가 실제 실행 뒤에 이것을 잰다.

## 결과 2: 나중 교환으로 페이지 확인 (D3, `dream-1`)

| 값 | 결과 |
|---|---|
| `verify` 후보 만들기 | 53.0초, 후보 44개, 페이지 22개 |
| 판단한 것 | 교환 1개와 `verify` 후보 8개 |
| 걸린 시간 | 58.5초 |
| 비용 | $0.234 |
| `none` | 9 |
| 제안할 것 | 0 |

- 후보를 만드는 53초는 대부분 페이지마다 하는 근거 모드 검색이다. 분리된 작업자에서 돌기 때문에 훅은 기다리지 않는다.
- 찾은 한계: 기본 임베딩 모델을 `e5-small`로 적은 결정 페이지는 지금 사실과 다르다. 그런데 이 페이지에 붙은 나중 교환은 주제만 비슷하고 모델을 바꾼다는 말이 없었다. 판단은 `none`이었고 그 판단은 맞다. 모델을 바꾼 교환이 검색 상위 5개(`VERIFY_SEARCH_LIMIT`)에 들지 못한 것이 원인이다.
- 그래서 D3의 재현율은 검색이 뒤집는 교환을 찾느냐에 달려 있다. 검색 한도를 올릴지는 재고 나서 정한다. 재지 않고 올리지 않았다.

## 결과 3: 심은 오류 시험 (D3, `dream-2`)

`tests/benchmarks/measure_dream_verify.py`. 사례는 모두 이 시험용으로 지은 것이다.

| 값 | 결과 |
|---|---|
| 사례 | 20 (한국어 10, 영어 10) |
| 심은 오류 | 10 (주장 표 페이지 8, 사실 하나짜리 페이지 2) |
| 음성 대조군 | 10 |
| 판단 묶음 | 3 (8, 8, 4) |
| 찾은 것 | 10 (`supersede_claim` 8, `update_memory` 2) |
| 놓친 것 | 0 |
| 잘못 올린 것 | 0 |
| 코드 확인에서 걸러진 것 | 0 |
| 페이지를 통째로 폐기한 것 | 0 |
| 정밀도 | 1.0 |
| 재현율 | 1.0 |
| 비용 | $0.135 |

- 처음 시험은 사례 이름(`...-control-...`)이 페이지 경로와 항목 키에 들어 있어 판단이 답을 볼 수 있었다. 검토에서 찾았고, 이름을 판단 순서 번호로 바꿔 다시 쟀다. 위 표가 다시 잰 값이다.
- 한 묶음 8개로 나눠 판단했고, 묶음마다 심은 오류와 대조군이 섞여 있으며 같은 페이지 글이 한 묶음에 두 번 나오지 않는다.
- 주장 표 페이지에서는 틀린 줄을 가리킨 `supersede_claim`만 찾은 것으로 센다. 다른 줄이 아직 맞으므로 통째 폐기는 오답이다.
- 음성 대조군은 여섯 가지다. 묻기만 함, 페이지와 같은 말, 이번 한 번만 예외, 같은 주제의 다른 일, 바꾸지 말라고 한 생각, 다른 프로젝트 이야기.
- 심은 오류는 "이제 X가 아니라 Y다"처럼 분명하고 10건뿐이다. 10건을 다 찾았다는 것은 재현율이 대략 0.7 이상이라는 정도만 말해 준다. 이 값은 프롬프트나 모델을 바꿨을 때 비교하는 기준으로만 쓴다.

## 결과 4: 드리밍 전 질문 세트 (C8)

`tests/benchmarks/measure_dream_backlog.py`. 질문 파일과 결과는 저장소 밖 `$HOME/workspace/vault-graph-eval/`에 있다.

- 대기 중인 세션 교환 198개 가운데 사용자가 친 글이 40자 이상인 139개를 에이전트가 읽고, 결정·규칙·교정·선호가 담긴 교환 26개를 골라 질문 26개를 썼다. 드리밍 판단과는 따로 골랐다.
- 질문은 10일, 세션 파일 15개에 걸쳐 있다. 한국어 22개, 영어 4개다.
- 질문마다 답이 있는 교환 위치(`<path> L<a>-L<b>`)를 적었다.

| 값 | 드리밍 전 (2026-11-19, `690a1b1`) |
|---|---|
| 질문 | 26 |
| 기억됨 (그 교환을 인용한 `wiki/` 페이지가 있음) | 0 |
| context hit (`build_context_pack`이 그 페이지를 돌려줌) | 0 |
| 오류 | 0 |

- 기억된 것이 0이라는 것은 이 질문들의 답이 지금 대기 교환에만 있다는 뜻이다.
- 드리밍을 켜고 제안을 승인한 뒤 같은 명령을 다시 돌리면 두 값이 얼마나 오르는지 나온다. 드리밍이 놓친 교환은 "기억됨"이 0으로 남는다.
- 질문 하나는 2026-11-04의 임베딩 모델 결정을 묻는다. 그 결정은 뒤에 바뀌었으므로, 이 질문은 "기억됨"이 되더라도 지금 사실과 다를 수 있다.
- 질문을 쓴 에이전트는 139개 중 약 38개에 남길 내용이 있다고 봤다(26개를 골랐고 12개쯤은 중복이라 뺐다). 이 수는 읽고 어림한 값이다.

## 통과 조건 상태

| 조건 (spec §7) | 상태 |
|---|---|
| 드리밍 제안 승인율이 처음 해결된 30개에서 0.7 이상 | 값 없음. `vg dream on` 뒤 사람이 제안을 해결해야 한다. `vg dream status`가 드리밍 제안만으로 센다 |
| 실행당 제안 수, 인용 확인이 거른 수 | dry-run 16개에서 제안 1, 거른 것 0 |
| 대기 교환에만 답이 있는 질문 20개 이상의 context hit 전후 | 질문 26개, 드리밍 전 0. 드리밍 뒤 값은 없다 |
| 기존 질문의 context hit이 떨어지지 않음 | 재지 않음. dry-run은 페이지를 바꾸지 않는다. 첫 승인 뒤 `measure_memory_recall`로 잰다 |
| 실행당 비용 | 교환 16개에 $0.40, `verify` 8개에 약 $0.2 |
| 대기 나이 중앙값 | 보고만 한다. 이번에는 바뀌지 않았다 |
| D3 심은 오류 시험 | 20건에서 정밀도 1.0, 재현율 1.0 |

## 남은 일

1. `vg dream on`으로 켜고 며칠 쓴 뒤 `vg dream status`의 승인율을 본다. 제안은 Vault에서 `review resolve`로 해결한다.
2. 제안을 승인하고 색인한 뒤 `measure_dream_backlog`를 같은 질문 파일로 다시 돌려 "기억됨"과 context hit을 드리밍 전 값(0, 0)과 비교한다.
3. 같은 때 `measure_memory_recall`로 기존 질문의 context hit이 떨어지지 않았는지 본다.
4. 해결된 제안이 30개가 되면 기본값(꺼짐)을 다시 정한다 (OD2).
5. "기억됨" 비율이 낮으면 프롬프트가 너무 많이 건너뛰는 것이다. 그때 프롬프트를 고치고 `PROMPT_VERSION`을 올린다.
6. `VERIFY_SEARCH_LIMIT`을 5에서 올렸을 때 뒤집는 교환을 더 찾는지 잰다.
