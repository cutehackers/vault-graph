# Vault 검색: 벡터 검색과 에이전트 직접 접근 토론 결과

작성일 2026-11-13. 저장소 기준 커밋 `c2df3af`. 비판 측(벡터 회의)과 옹호 측(벡터 지지) subagent가 각자 코드와 실제 Vault를 읽기 전용으로 조사하고, 1차 주장과 반박을 한 번씩 주고받았다. 원문과 실험 파일은 세션 scratchpad `debate/` 폴더에 있다(저장소 밖).

## 1. 질문

Vault 검색에 벡터(임베딩)를 쓸 의미가 있는가. 에이전트가 Vault 파일을 직접 읽어 가져오는 편이 더 좋은 결과를 더 싸게 얻지 않는가. 특히 기억(wiki의 decision, rule 등)과 세션 원문(`raw/sessions`)에서.

## 2. 결론

"벡터 대 직접 접근"은 잘못 고른 축이다. 실측에서 검색 품질을 가른 것은 세 가지였다.

1. 질의 언어. 한국어 질문을 그대로 넣으면 `vg search` recall@1 0.25, 에이전트가 영어 키워드로 바꿔 넣으면 0.95다.
2. 사람이나 에이전트가 쓴 짧은 요약(frontmatter `summary`). 이것을 읽고 고르면 1.00, 같은 영어 키워드로 본문 grep을 하면 0.05다.
3. 검색 단위의 품질. 세션 원문은 턴 머리줄 78%가 도구 이름뿐이고 사본이 중복돼 있어, 벡터와 키워드 모두 엉뚱한 조각을 올린다.

벡터는 이 셋 위에 얹는 보조 신호다. 영어 질의에서 키워드만 쓸 때보다 recall@1을 0.70에서 0.95로 올리므로 wiki에서는 값을 한다. 세션 원문에서는 지금 구현으로는 날짜로 좁힌 grep에 진다.

## 3. 토론 결과 요약

### 양측이 합의한 것

- 합의1. 한국어 실패(recall@1 0.25)의 원인은 벡터 방식이 아니라 e5-small의 같은 언어 편향과 질의 형식이다. 가장 싼 해결책은 에이전트가 영어 키워드로 바꿔 질의하는 것이다. MCP 도구 `search_vault`, `build_context_pack`에 설명이 없어 지금은 이 규칙을 전달할 방법이 없다(`mcp_tools.py:843-864`).
- 합의2. wiki 기억은 현재 규모(personal 124페이지, 요약 합계 약 1,800단어)에서 카탈로그(title, summary, type, tags)를 에이전트가 직접 읽고 고르는 방식이 가장 정확하다. 블라인드 실험에서 한국어 질문 20/20, 읽기 2번이었다. 카탈로그는 페이지당 약 216바이트라 약 900페이지까지 맥락에 들어간다(추정, 지금 속도로 약 3년).
- 합의3. wiki에서 하이브리드 검색은 유지한다. 영어 키워드 기준 키워드 단독 0.70, 벡터 단독 0.55, 융합 0.95다. 키워드가 33위로 놓친 정답을 벡터가 3위로 잡아 융합 1위가 된 사례가 있다.
- 합의4. 세션 원문에서 현재 `vg search`는 결정 질문을 놓친다. "arctic을 기본 모델로 바꾸기로 어떻게 결정했지"는 자연어 질의로 한·영 모두 10위 밖, 한 번에 약 8초다. 날짜로 좁힌 grep은 호출 2번, 약 0.01초에 정답 줄을 찾았다. 원인은 날짜 신호가 없는 순위와 RRF에서 벡터 1위가 8위로 밀리는 융합 방식이다.
- 합의5. 세션 원문 정리(도구만 있는 턴 제거, 사본 합치기, 질문과 답을 한 조각으로)는 벡터를 쓰든 안 쓰든 해야 한다.
- 합의6. 질의 텍스트와 그 뒤에 연 경로를 기록해야 한다. 지금은 기록하지 않아(`usage_log.py`) 실제 성공률을 아무도 모른다. 비용이 큰 벡터 쪽(전체 색인 14~21분, 최대 21GB)이 효과를 증명해야 한다는 점에도 양측이 동의했다.

### 각자 철회한 것

- 비판 측은 "벡터를 기본에서 끈다"를 철회했다. 영어 질의 융합 0.95를 근거로.
- 옹호 측은 "wiki 기억 검색의 주 경로는 벡터"를 철회했다. 카탈로그 20/20을 근거로. 세션 원문의 기본 경로도 날짜·project로 좁힌 grep으로 인정했다.

### 남는 이견

- 이견1. 날짜도 모르고 겹치는 단어도 없는 세션 질문("그때 그 오류 어떻게 넘어갔지")에서 grep 재시도와 세션 벡터 색인 중 어느 쪽이 나은가. 옹호 측은 세션 벡터 색인을 선택 기능으로 남기자고, 비판 측은 색인 자체가 필요 없다고 본다. 둘 다 이 경우를 재지 않았다. 옹호 측이 낸 사례 하나("MCP 도구가 안 보였을 때")는 벡터와 grep이 모두 실패했다.
- 이견2. 세션을 요약 카탈로그로 만들면 지금 속도로 약 80일 뒤 맥락 예산(약 5만 토큰)을 넘는다(추정). 그 뒤에 필요한 것이 FTS인지 벡터인지 정하지 못했다.

## 4. 세션과 기억에 맞는 검색 구조

| 대상 | 1단계 | 2단계 | 벡터 역할 |
|---|---|---|---|
| wiki 기억 | 카탈로그(summary 목록)를 에이전트가 읽고 고름 | 페이지 본문 읽기, `related` 한 단계 | 페이지가 많은 Vault에서 영어 키워드와 함께 하이브리드로 후보 좁히기 |
| 세션 원문 | 파일 이름 날짜, frontmatter `project`로 범위 좁히기 | 좁힌 파일에 grep, 파일별 일치 수부터 보기 | 미정(이견1). 지금 구현은 grep보다 못함 |
| 세션에서 나온 결정 | 세션 원문을 다시 찾지 말고 wiki 결정 페이지로 정리 | wiki 경로를 따름 | wiki와 같음 |

마지막 줄이 이 질문의 근본 답에 가깝다. 비판 측 실험에서 arctic 결정을 찾을 때 knowledge 모드 1위가 이미 뒤집힌 e5-small 결정 페이지였다. 결정이 세션 원문에만 있고 wiki에 반영되지 않으면, 어떤 검색 방식으로도 "현재 유효한 기억"을 정확히 돌려줄 수 없다. 검색 방식보다 세션에서 결정을 wiki로 옮기는 정리 단계가 품질을 더 크게 좌우한다.

## 5. 다음 행동 제안

- 답변1. MCP 검색 도구에 설명과 질의 예시를 붙인다. "한국어 질문은 영어 핵심어 3~4개로 바꿔 질의하라"를 포함한다. 비용이 가장 작고 효과가 가장 크다(0.25 → 0.95).
- 답변2. wiki 카탈로그(title, summary, type, status, tags)를 MCP 리소스 하나로 제공한다.
- 답변3. 질의 텍스트와 그 뒤에 연 경로를 기록한다. 이후 모든 판단의 근거가 된다.
- 답변4. 세션 원문 조각을 정리한다(도구만 있는 턴 제거, 사본 합치기).
- 답변5. 이견1을 정할 측정 세트를 만든다. 사람이 쓴 모호한 세션 질문을 영어로 바꿔 grep, 키워드 색인, 하이브리드를 비교한다. 결과가 나오기 전까지 세션 벡터 색인을 늘리는 작업(모델 교체 포함)은 보류한다.

## 6. 이 결론의 한계

- 질문은 모두 에이전트가 정답 페이지를 보고 썼다. 블라인드 실험도 질문 작성은 블라인드가 아니다.
- wiki는 personal Vault 64~124페이지, 세션은 vault-graph Vault 55파일만 쟀다. 표본이 작다(wiki 20문항과 8문항, 세션 5문항과 결정 질문 1개).
- `vg search` 약 8초는 CLI 호출마다 모델을 올리는 시간을 포함한다. MCP 서버가 상주할 때의 지연은 재지 않았다.
- 같은 20문항에서 arctic-m의 recall@1은 재지 않았다.
