## 5. 발견

1. 발견A. 검색 한 번마다 준비 상태 검사가 전체 조각을 다시 읽는다. `search_readiness_service.py:40`의 `check`가 벡터 stale 수를 세려고 `vector_index_adapter.py:171`의 `plan`을 부르고, `plan`은 조각 약 41만 행을 SQLite에서 읽어 객체로 바꾼다. 표본 4문항 프로파일에서 이 검사가 검색 시간의 약 70%였다. 층2(벡터 203개)는 0.1초, 층1(벡터 38,410개)은 34초다. 이 검사를 고치지 않으면 목표8을 만족할 수 없다.
2. 발견B. 기본 검색 모드는 Vault의 `docs/`를 보지 않는다. Vault 사용법(`docs/usage.md`), 에이전트 규칙(`docs/agent/*`), personal의 설계 문서(`docs/superpowers/specs/*`)가 여기에 든다. 에이전트가 모드를 지정하지 않으면 이 17문항은 0건 적중이다. 설계 문서가 운영 계약과 같은 역할로 분류되는 것도 의도인지 확인이 필요하다.
3. 발견C. 층2는 천장에 닿아 개선을 가리지 못한다. 실제 Vault의 어려움(공통 틀 페이지 사본 6개, 같은 대화의 세션 사본, 영어 제목과 한국어 질문)을 더 넣어야 한다.
4. 발견D. 답 없음 문항은 채점하지 못한다. 검색은 언제나 결과를 내고, 결과에 "확신 낮음" 신호가 없다.

## 6. 목표 제안

spec 2.1에 제안으로 적었다. 근거는 아래와 같다.

1. 에이전트는 상위 5개를 읽는다. 기억 질문 10개 중 1개를 놓치는 수준(recall@5 0.90)을 제품 수준으로 본다.
2. 지금 recall@10은 0.89다. 순위 손실의 절반은 6~10위에 있으므로 재순위나 점수 결합만으로 recall@5를 0.89 근처까지 올릴 수 있다. 0.90을 넘으려면 후보 손실 11문항(의역 4, 세션 6)도 줄여야 한다(방안A·B).
3. 종류별 목표 0.85는 지금 가장 낮은 방법(0.73)과 세션(0.75)에서 4~6문항을 더 맞히는 값이다. 층1은 종류마다 30~60문항이라 한 문항이 1.7~3.3점이다. 이보다 촘촘한 목표는 측정 잡음과 구분되지 않는다.
4. 검색 시간 1초는 MCP 도구를 대화 중에 여러 번 불러도 사용자가 기다림을 느끼지 않는 값이다. 층2 결과(0.1초)로 보아 발견A를 고치면 닿을 수 있다.
5. LongMemEval은 보조 지표다. 영어 일상 대화라서 떨어지지 않는지만 본다(결정5).
