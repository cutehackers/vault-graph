## 1. 질문을 만든 방식

### 1.1 사용자 질문 패턴 분석

- 대상: Vault 6개(personal, vault-graph, vault-builder, bake, sgp-981-app, 981park-flutter-app)의 세션 기록에 있는 사용자 발화 464개. 시스템이 붙인 블록과 붙여넣은 로그는 뺐다.
- 기억을 되찾는 질문은 71개(15%)다. 세부 유형은 상태(됐나, 머지됐나) 28%, 방법 23%, 과거 세션 내용 15%, 결정 이유 11%, 사용자가 붙인 코드의 뜻 8%, 위치 7%, 사실 7%다.
- 기억을 되찾는 질문의 약 60%는 답이 세션 기록에만 있다.
- 언어는 한국어·영어 혼용 47%, 한국어만 39%, 영어만 14%다. 길이 중앙값은 38자다. "언제"를 묻는 질문은 0건이다.
- wiki 제목은 거의 모두 영어이고 aliases가 있는 페이지는 0개다. 한국어 질문으로 영어 페이지를 찾는 경우가 기본 형태다.
- 분석 원문과 문장 틀은 저장소 밖(`~/.vault-graph-eval/layer1/patterns.md`)에만 있다. 회사 Vault 문장은 그 파일에도 형태만 남겼다.
- team Vault는 회사 저장소에 연결된 sgp-981-app과 981park-flutter-app으로 보았다[가정]. vault-map에 role이 team인 Vault가 없다.

### 1.2 질문 작성 규칙

- 질문은 검색 도구를 쓰지 않는 별도 에이전트가 Vault 파일을 직접 읽고 썼다(2026-11-07 사용자 결정).

### 3.1 질문 세트를 고친 것

처음 236문항에는 Vault의 `docs/` 아래 문서만 정답인 문항이 17개 있었다(모두 personal, usage.md 8, 설계 문서 5, 에이전트 규칙 4). `docs/`는 `operating_contract` 역할로 분류되고(`src/vault_graph/indexing/ingestion/document_authority.py:35`), 기본 모드 `knowledge`는 그 역할을 검색하지 않는다(`src/vault_graph/retrieval/search/retrieval_service.py:56`). 그래서 모두 후보 손실이었다.

- 기본 모드가 `docs/`도 찾게 바꿔 잰 결과(2026-11-12): 17문항 중 15문항이 맞았지만 wiki 질문 7문항이 나빠졌고 후보 손실이 11문항에서 23문항으로 늘었다.
- `docs/`는 Vault 운영 규칙과 틀 문서라서 wiki 내용을 찾는 검색과 맞지 않는다. 이 17문항도 질문 작성 에이전트가 파일을 읽고 만든 것이고, 사용자 질문 기록에서 온 것이 아니다.
- 그래서 기본 검색에 `docs/`를 넣지 않고 17문항을 층1에서 뺐다(spec 결정14). title이 30문항 아래로 내려가지 않게 personal 위키 페이지로 title 3문항(`L1A-091`~`L1A-093`)을 더했다. 아직 정답으로 쓰지 않은 페이지 목록에서 검색 도구 없이 골랐다.
- 뺀 뒤 종류마다 sha256(id) 순으로 개발용과 시험용을 다시 나눴다. 위 표는 그 값이다.

## 5. 발견

1. 발견A. 검색 한 번마다 준비 상태 검사가 전체 조각을 다시 읽는다. `search_readiness_service.py:40`의 `check`가 벡터 stale 수를 세려고 `vector_index_adapter.py:171`의 `plan`을 부르고, `plan`은 조각 약 41만 행을 SQLite에서 읽어 객체로 바꾼다. 표본 4문항 프로파일에서 이 검사가 검색 시간의 약 70%였다. 층2(벡터 203개)는 0.1초, 층1(벡터 38,410개)은 34초다. 이 검사를 고치지 않으면 목표8을 만족할 수 없다. 2026-11-12에 고쳤다(spec 4.2.6, 작업 24). 층1 192문항 기준 검색 p50 0.13초, p95 0.30초이고, 층1·층2 모든 문항의 순위가 기준값과 같다.
2. 발견B. 기본 검색 모드는 Vault의 `docs/`를 보지 않는다. 넣어 보니 wiki 정답이 밀렸고, `docs/`는 wiki 내용 검색에 쓸모가 적어서 지금대로 둔다(3.1, spec 결정14).
3. 발견C. 층2는 천장에 닿아 개선을 가리지 못한다. 실제 Vault의 어려움(공통 틀 페이지 사본 6개, 같은 대화의 세션 사본, 영어 제목과 한국어 질문)을 더 넣어야 한다.
4. 발견D. 답 없음 문항은 채점하지 못한다. 검색은 언제나 결과를 내고, 결과에 "확신 낮음" 신호가 없다.

## 6. 목표 제안

spec 2.1에 적었고 사용자가 확정했다(결정8, 2026-11-11). 근거는 아래와 같다.

1. 에이전트는 상위 5개를 읽는다. 기억 질문 10개 중 1개를 놓치는 수준(recall@5 0.90)을 제품 수준으로 본다.
2. 지금 recall@10은 0.88이다. 순위 손실 29문항 중 17문항이 6~10위에 있으므로 재순위나 점수 결합만으로 recall@5를 0.88 근처까지 올릴 수 있다. 0.90을 넘으려면 후보 손실 11문항(의역 4, 방법 1, 세션 6)도 줄여야 한다(방안A·B).
3. 종류별 목표 0.85는 지금 가장 낮은 방법(0.69)과 세션(0.75)에서 각각 6문항을 더 맞히는 값이다. 층1은 종류마다 30~60문항이라 한 문항이 1.7~3.3점이다. 이보다 촘촘한 목표는 측정 잡음과 구분되지 않는다.
4. 검색 시간 1초는 MCP 도구를 대화 중에 여러 번 불러도 사용자가 기다림을 느끼지 않는 값이다. 층2 결과(0.1초)로 보아 발견A를 고치면 닿을 수 있다.
5. LongMemEval은 보조 지표다. 영어 일상 대화라서 떨어지지 않는지만 본다(결정5).
