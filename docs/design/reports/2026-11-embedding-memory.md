# 측정 A-16: 전체 재색인의 메모리와 시간, ONNX 아레나 켬·끔 (2026-11-06)

spec 2026-11-05-session-memory-indexing, 작업 #20. 코드: #2 토큰 예산 배치(`9857af8`), #17 임베딩 캐시, 세션 조각기 등록(`3cac571`) 전.

## 방법

이 Mac의 실제 Graph Home에서 `vg index --all-vaults --full`을 두 번 돌렸다. 매번 임베딩 캐시 파일을 지워 모든 조각을 실제로 임베딩했다. 둘째 run은 설정 기본값을 바꾸는 작은 실행기로 `cpu_mem_arena=False`를 넣었다. `/usr/bin/time -l`로 시간과 최대 RSS를 쟀다. 측정 중 다른 테스트 실행이 같은 컴퓨터에서 돌았으므로 시간은 넉넉히 본다.

| 아레나 | 문서 | 벡터 upsert | 시간 | 최대 RSS | 종료 |
|---|---|---|---|---|---|
| 켬(기본) | 547 | 53,795 | 463초 | 7.49GB | 0 |
| 끔 | 547 | 53,795 | 571초 | 7.72GB | 0 |

비교 기준(조사 index-performance): 전체 재색인 최대 RSS 21.2GB, 26k 조각 약 830초.

## 판단

- 최대 RSS는 21.2GB에서 7.5GB로 65% 줄었다. 목표2 "6GB 이하"([가정])는 아직 못 미친다.
- 시간은 조각이 두 배 넘게 많은데도 830초보다 짧다(A-16 시간 조건 충족).
- 아레나를 끄면 23% 느려지고 메모리는 줄지 않았다. spec §4.3.4 규칙(20% 넘게 느리면 켬 유지)대로 기본값을 켬으로 둔다.
- 이 run의 세션 파일은 아직 일반 조각기로 잘렸다. 세션 조각기(`3cac571`)가 조각 수를 크게 줄이므로, 목표2는 작업 #31의 재측정에서 다시 판단한다. 그때도 6GB를 넘으면 `embedding_token_budget`을 줄이는 것을 사람에게 묻는다(spec 5.5).

## 다시 잰 값: 세션 조각기 적용 뒤 모든 Vault (2026-11-06, 리뷰 발견3)

실제 Graph Home 복사본에서 이 브랜치로 `vg index --all-vaults --full`을 다시 돌렸다. 임베딩 캐시는 꺼서 모든 조각을 실제로 임베딩했다. 세션 조각은 모두 `session-exchange-v1`이다(이 Mac의 세션 파일은 아직 v1이다).

| 토큰 예산 | 문서 | 벡터 upsert | 일반 조각 / 세션 조각 | 시간 | 최대 RSS |
|---|---|---|---|---|---|
| 16,384 | 549 | 14,441 | 5,678 / 8,763 | 326초 | 6.85GB |
| 8,192 | 549 | 14,441 | 5,678 / 8,763 | 321초 | 4.29GB |

- 세션 조각기만으로 벡터가 53,795개에서 14,441개로, 시간이 463초에서 326초로 줄었다.
- 토큰 예산 16,384에서는 목표2(6GB 이하)를 0.85GB 넘는다. 8,192에서는 4.29GB로 목표를 맞추고 시간은 같다.
- 그래서 기본 `embedding_token_budget`을 8,192로 바꿨다. spec §4.3.4의 16,384는 측정으로 정할 [가정] 값이었다.
- 아레나 기본값(켬)은 그대로다.
