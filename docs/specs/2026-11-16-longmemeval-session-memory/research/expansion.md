# 사실 키를 붙이는 방식: 일반 검색의 경험

조사일: 2026-11-17. 측정은 scratchpad `B-claude`, `B-fail` 작업 공간(사실이 있는 40문항)에서 했다.

### X26. 사실이 있는 40문항에서 가중치 0.5는 거의 효과가 없고 1.0 이상에서 오른다
- source: scratchpad `fact_weight.py` 결과(2026-11-17)
- basis: X22

정답 세션을 모두 상위 5개에 넣은 문항: 사실 없음 18, 가중치 0.5 19, 1.0 23, 2.0 이상 26. 나빠진 문항은 없다. 추적해 보면 사실은 원문에 없는 낱말로 정답 세션을 맞히지만(예: "악기" 질문에서 기타·피아노·드럼 사실이 벡터 4~19위), 0.5를 곱하면 주제만 비슷한 다른 세션에 밀린다. 이 40문항으로 값을 골랐으므로 그 밖에서의 효과는 모른다.

### X27. 논문에서는 사실을 원문과 한 키로 합칠 때가 따로 색인해 순위를 합칠 때보다 훨씬 낫다
- source: arXiv 2410.10813v2 §5.3, Table 3, 부록 E.2·E.3 (2026-11-17 읽음)
- basis:

세션 값 recall@5: 원문 키만 0.706, 사실 키만 0.642, 원문+사실 한 키(키 합치기) 0.732, 사실을 따로 검색해 순위 합치기 0.618. 논문은 순위 합치기가 원문 하나당 키를 사실 수만큼 늘려 약하다고 본다. BM25, Contriever, Stella 모두에서 키 합치기가 원문만 쓸 때보다 recall@5가 높다.

### X28. 문서 확장은 일반 기법이고, 생성 문장의 잡음을 줄이면 더 낫다
- source: Doc2Query--, ECIR 2023, arXiv 2301.03266 (2026-11-17 검색)
- basis:

문서에서 생성한 질문을 문서 키에 덧붙이는 확장에서, 원문과 관련이 약한 생성 문장을 걸러 내면 검색 효과가 최대 16% 오르고 색인이 33% 준다고 보고한다.

### X29. 가중치를 두는 순위 합치기는 자기 데이터로 맞출 수 있을 때만 쓰고 기본은 같은 무게다
- source: MongoDB hybrid search 문서, Elastic hybrid retrieval 글, Zvec 재정렬 문서 (2026-11-17 검색)
- basis:

RRF는 상수 60과 같은 무게가 기본이고, 신호별 가중치는 자기 데이터로 조정할 수 있을 때 권한다. 자기 질문에 맞춘 가중치는 그 밖에서 효과가 보장되지 않는다.

### X30. 교환마다 사실을 묶은 확장 키 하나는 사실마다 키 하나보다 나빴다
- source: scratchpad `fact_weight.py` 결과, 커밋 `18b4383`으로 다시 색인한 40문항(2026-11-17)
- basis: X26, X27, I1

교환 하나의 사용자 질문 제목과 사실들을 한 조각으로 묶으면, 같은 40문항에서 가중치 1.0과 2.0 모두 20문항이다. 사실마다 키 하나일 때(1.0에서 23, 2.0에서 26)보다 낮다. 한 조각에 여러 사실이 섞여 기타·피아노처럼 구체적인 항목과의 의미 일치가 약해졌다. 이 조각은 원문 창과 따로 순위가 합쳐지므로 논문의 키 합치기(원문+사실 한 키)와 같지 않다. 원문 창을 그대로 두는 규칙(I1) 때문에 논문 방식 그대로는 만들 수 없다.

### X31. 이번 B·C 측정은 표본이 작고 논문 조건과 다르다
- source: arXiv 2410.10813v2 §1, §3.4, §5.3, §5.4 (2026-11-18 읽음); 이번 측정 기록
- basis: X25, X27

논문은 500문항이고, 사실 키와 시간 범위 실험은 LongMemEval_M(질문마다 대화 약 500개, 약 150만 토큰)에서 했다. 이번에는 LongMemEval_S(질문마다 대화 약 50개)에서 B를 40문항, 개정 C를 범위가 붙는 10문항으로 쟀다. 40문항에서 1문항은 2.5%이고, 시범 20문항은 쉬운 앞쪽 문항, 나머지 20문항은 A가 틀린 문항만 골랐다. 이 숫자로는 가중치나 저장 방식의 우열을 말할 수 없다.
