## 2. Intent

검색 품질과 기억 품질에 목표 숫자를 두고, 변경할 때마다 로컬에서 그 숫자를 확인하며, 목표에 닿을 때까지 개선한다.

1. 의도1. 평가를 믿을 수 있게 만든다. 질문 수를 늘리고, 정답을 잃는 단계를 기록하고, 명령 하나로 돌린다.
2. 의도2. 검색 품질을 올린다. 단계별 손실 기록이 가리키는 곳부터 고친다.
3. 의도3. 기억 품질을 올린다. 쓰는 시점에 페이지를 찾기 쉽게 만들고, 정리가 밀리지 않게 한다.
4. 의도4. 기억이 검색에 닿는 경로를 지킨다. 색인 실패가 보이고, 색인 전에도 키워드 검색이 된다.

## 3. Non-goals

- 도구 안에서 LLM을 부르는 일. 질의 재작성, 답변 합성, 채점에 LLM을 쓰지 않는다.
- 원격 HTTP, 인증, 호스팅, 팀 공유.
- 외부 데이터 연결(메일, 메신저, 회의록).
- CI에서 검색 품질 평가를 돌리는 일. 사용자 지시(2026-11-11)로 로컬에서만 돌린다.
- 임베딩 모델 교체. 4.3의 조건을 만족할 때만 별도 spec으로 연다.
- LongMemEval의 답변 정확도 측정. 답을 쓰는 LLM과 채점 LLM이 필요하다.

## 4. Design

### 4.1 평가 (의도1)

#### 4.1.1 평가 세트 세 층

| 층 | 내용 | 위치 | 쓰임 |
|---|---|---|---|
| 층1 | 실제 Vault로 만든 질문. 한국어 중심. wiki와 세션. | 저장소 밖 | 변경을 넣을지 정하는 주 지표 |
| 층2 | 가상 Vault와 질문. 한국어와 영어 코딩 기억. | 저장소 안 `tests/fixtures/` | 누구나 같은 숫자를 다시 낸다 |
| 층3 | LongMemEval-S(cleaned), 검색 단계만 | 데이터는 내려받는다. 변환기만 저장소에 둔다 | 외부 기준. 릴리스 전 확인 |

- 층1과 층2의 종류: 제목 그대로, 의역, 결정, 방법, 세션, 답 없음. 종류마다 30문항 이상이다.
- 질문은 검색 도구를 쓰지 않는 별도 에이전트가 만든다(2026-11-07 사용자 결정 유지).
- 층1과 층2는 개발용과 시험용으로 반씩 나눈다. 조정은 개발용으로 하고, 시험용은 채택 판정에만 쓴다.

#### 4.1.2 평가 도구

- 한 프로세스에서 모든 질문을 돌린다. 검색 서비스를 직접 부른다.
- 문항마다 아래를 기록한다.
  1. 정답의 키워드 순위, 벡터 순위, 그래프 순위
  2. 합친 뒤 조각 순위
  3. 문서로 접은 뒤 최종 순위
  4. 검색 시간
- 문항을 세 가지로 나눈다: 적중(5위 안), 순위 손실(후보에는 있고 5위 밖), 후보 손실(어느 신호의 후보에도 없음).
- 출력: 종류별 recall@5, recall@10, MRR, 손실 분류표, 검색 시간 p50과 p95.
- 기존 `measure_session_recall.py`와 `measure_memory_recall.py`의 채점 규칙은 그대로 쓴다.

#### 4.1.3 기준값과 비교

- 층2와 층3의 기준 점수 파일을 저장소에 둔다. 층1은 숫자만 둔다(질문 원문 없음).
- 비교 명령은 종류별 차이와 "좋아진 문항 N개, 나빠진 문항 M개"를 출력한다.
- 검색이나 색인 코드를 바꾼 PR은 이 출력을 본문에 붙인다.
- 채택 규칙: 층1 시험용이 좋아지고, 층3이 기준값에서 1점 넘게 떨어지지 않고, 목표4와 목표5가 유지되면 넣는다.

#### 4.1.4 LongMemEval 변환기

- 질문 하나의 대화 기록 묶음을 정규화 JSONL(`vg-session-jsonl/1`)로 바꾼다.
- Vault 도구 `sessions capture --normalized`가 임시 Vault에 세션 파일을 쓴다. vault-graph는 Vault 파일을 직접 쓰지 않는다.
- `vg index` 뒤 `--mode evidence` 검색을 돌리고, 상위 5개 결과의 세션이 `answer_session_ids`를 모두 포함하는지 센다.
- 먼저 20문항으로 문항당 시간을 잰다. 전체 470문항이 2시간 안이면 전체로 돌리고, 넘으면 고정 표본 150문항으로 줄인다(결정10).
- 시작 전에 LongMemEval-V2가 코딩 에이전트에 더 맞는지 확인한다.

### 4.2 검색 품질 (의도2)

4.1.2의 손실 분류표를 먼저 낸다. 그 표에 따라 아래에서 고른다.

#### 4.2.1 방안A 여러 표현 질의 (후보 손실 대응)

- `search_vault`와 `build_context_pack`이 `queries`(문자열 최대 4개)를 받는다. 기존 `query` 하나도 그대로 받는다.
- 표현마다 후보를 뽑고 같은 RRF 식으로 합친다. 같은 색인과 같은 입력이면 같은 결과다.
- 도구 설명에 무엇을 넣을지 적는다: 한국어 표현, 영어 표현, 핵심 단어만, 예상되는 답 문장.
- 표현을 만드는 것은 호출하는 에이전트다. 도구 안 LLM 호출은 없다.
- 평가는 질문마다 표현 묶음을 미리 만들어 고정해 둔다.

#### 4.2.2 방안B 페이지 보강 필드 색인 (후보 손실 대응)

- 4.3.1에서 채운 summary, aliases, 답하는 질문을 페이지 카드 임베딩 입력과 키워드 표의 title·aliases 열에 넣는다.
- 답하는 질문 필드는 Vault frontmatter 규칙에 없다. summary와 aliases만으로 먼저 재고, 그 결과를 보고 vault-builder에 요청할지 정한다(결정11).

#### 4.2.3 방안C 로컬 재순위 모델 (순위 손실 대응)

- 조건: 순위 손실이 실패 문항의 절반 이상일 때만 진행한다.
- 상위 30~50개 문서를 교차 인코더로 다시 정렬한다.
- 설치된 fastembed 0.8.0의 기본 목록에는 맞는 모델이 없다. `BAAI/bge-reranker-base`는 중국어와 영어용이고, `jinaai/jina-reranker-v2-base-multilingual`은 비상업 라이선스다.
- 후보는 `bge-reranker-v2-m3`(Apache-2.0)다. 직접 등록해야 한다. 채택 전에 이 Mac에서 검색 시간과 메모리를 잰다. 목표8을 넘으면 넣지 않는다.

#### 4.2.4 방안D 합치는 방식과 한국어 형태소

- 조사 문서(`2026-11-05-session-memory-indexing/research/search-quality-external.md`)의 권고7(Kiwi 형태소 열)과 권고8(점수 결합 비교)을 4.1 도구로 잰다.
- 좋아진 문항이 나빠진 문항보다 많고 어느 종류도 떨어지지 않을 때만 넣는다.

#### 4.2.5 임베딩 모델 교체 조건

- 방안A~D를 적용한 뒤에도 후보 손실이 실패 문항의 절반 이상이면 별도 spec을 연다.

|---|---:|---|
| 준비 상태 검사: 벡터 stale 수 | 15.2초 | Vault마다 색인 계획을 세운다. 조각 전체와 벡터 목록 전체를 읽는다(`read_only_service_factory.py` `VectorIndexerStaleCounter`) |
| 준비 상태 검사: 저장소 revision | 18.5초 | Vault마다 조각 전체와 벡터 목록 전체를 다시 읽는다(`search_readiness_service.py` `_store_revisions`) |
| 벡터 검색 | 10.0초 | Vault마다 벡터 메타데이터 행 전체를 SQLite에서 읽고 cosine을 계산한다(`vector_search/sqlite_reader.py` `search`) |

첫 수정 뒤 다시 잰 결과, 세션 검색(evidence 모드)은 아래 세 곳이 더 느렸다. 모두 고쳤다.

| 단계 | 하는 일 |
|---|---|
| 결과마다 근거 모으기 | 결과의 출처 묶음(provenance family)에 든 조각을 모두 읽는다. 쓰는 것은 문서마다 첫 조각뿐이다 |
| 앞뒤 문맥 붙이기 | 맞은 조각 앞뒤 하나를 붙이려고 세션 문서 전체(조각 2,000개 넘음)를 읽는다 |
| 키워드가 맞은 필드 찾기 | 후보마다 필드마다 FTS 질의를 한 번씩 낸다. 긴 질문에서 1.4초다. 검색 순위는 이 값을 쓰지 않는다 |

- 벡터 읽기: 읽기 전용 Chroma 읽기가 벡터 목록과 벡터를 프로세스 메모리에 둔다. SQLite 파일과 `-wal` 파일의 inode, 크기, 수정 시각이 바뀌면 다시 읽는다. 이 값은 읽기 전에 확인한다. 그래서 읽는 도중 커밋이 들어오면 다음 검색에서 다시 읽는다. 벡터 크기는 한 번만 계산하고, 내적은 `math.sumprod`로 계산한다.
- 준비 상태 검사: stale 수와 저장소 revision을 메타데이터 SQLite와 벡터 SQLite 파일의 같은 값, 임베딩 모델로 묶어 프로세스 안에 둔다. 파일이 그대로면 다시 계산하지 않는다. 저장소 상태 검사(health)와 모델 파일 확인은 매번 한다.
- 근거 모으기: 메타데이터 저장소가 묶음의 문서마다 첫 조각만 돌려준다(`list_family_document_evidence`). 한 검색 안에서 같은 묶음은 한 번만 읽는다.
- 문맥 붙이기: 메타데이터 저장소가 맞은 조각과 앞뒤 본문 조각만 돌려준다(`list_document_chunk_window`). 전체를 읽어 고르던 것과 같은 조각이다.
- 색인 두 개를 더한다: `chunks(vault_id, document_id, document_order)`, `chunks(vault_id, provenance_family_id)`. 기존 Graph Home에는 다음 `vg index` 때 생긴다. 없어도 검색은 되고 느릴 뿐이다.
- 키워드 검색은 검색 서비스가 부를 때 맞은 필드를 찾지 않는다(`KeywordQuery.with_matched_fields=False`). 다른 호출은 지금처럼 찾는다.
- 검색 결과와 순서는 바뀌지 않는다. `math.sumprod`는 확장 정밀도로 더해서 점수가 마지막 자리(약 1e-16)에서 다를 수 있다. 층1·층2 모든 문항의 순위가 기준값과 같은 것으로 확인한다(A-15).
- 새 의존성을 넣지 않는다.
- 첫 검색은 지금처럼 읽는다. 목표8은 한 프로세스에서 모델 적재 뒤 값이다. MCP 서버처럼 오래 도는 프로세스가 대상이다.

### 4.3 기억 품질 (의도3)

#### 4.3.1 쓰는 시점 보강

- `remember`와 `update_memory`가 `summary`(한두 문장)와 `aliases`를 받는다. `questions`(이 페이지가 답하는 질문 최대 5개)는 결정11의 측정 뒤에 정한다.
- 값은 호출하는 에이전트가 쓴다. vault-graph는 값을 만들지 않는다(AGENTS.md: 기계가 만든 내용을 Vault에 쓰지 않는다).
- Vault에 쓰는 것은 지금처럼 `publish-draft`와 `review propose`다. summary와 aliases를 Vault 검증이 받는지는 S7을 시작할 때 확인한다.
- `basis`가 `stated`인 `remember`에 summary가 없으면 결과에 경고를 넣는다. 거절하지는 않는다.

#### 4.3.2 기존 페이지 보강

- 정리 꾸러미(`curate_memory`)에 "summary 없는 페이지" 목록을 더한다.
- 에이전트가 정리 때 `update_memory`로 채운다. 한 번에 다루는 개수에 상한을 둔다.

#### 4.3.3 정리가 밀리지 않게 한다

- 세션 시작 회상의 "정리 대기" 줄에 나이 중앙값을 넣는다.
- 나이 중앙값이 목표7을 넘으면 그 줄을 회상 맨 위로 올리고 "지금 정리가 필요하다"고 적는다.
- 정리를 사람 없이 일정에 따라 돌리지 않는다(결정12). 정리는 사용자가 있는 세션에서만 일어난다.

#### 4.3.4 기억 품질 지표

- 기존 지표1~6을 유지한다.
- 더하는 지표: 지표7 summary가 있는 기억 페이지 비율(목표6). 지표8 `fetched` 사건이 있는 세션 비율.
- 지표3(주입 대비 열람)은 계속 기록만 한다. 세션 시작 회상은 질문과 상관없이 같은 목록을 넣으므로 낮은 값이 정상일 수 있다(보고서 `2026-11-memory-quality.md`).
- 검색 질의 기록: 에이전트가 던진 질의와 그 뒤에 연 페이지를 `usage/`에 남긴다. Graph Home 안에만 두고 Vault에는 쓰지 않는다. 층1 질문을 고르는 재료로 쓴다(결정13).

### 4.4 기억이 검색에 닿는 경로 (의도4)

#### 4.4.1 색인 실패를 회상에 보인다 (승인됨, 2026-11-11)

- 벡터 실패 경고를 표준 오류와 함께 회상 출력(표준 출력)의 "가져오는 방법" 절에도 한 줄 넣는다.
- 백그라운드 따라잡기 프로세스가 벡터 밖의 이유로 죽은 경우도 같은 기록에 남긴다.
- `vg doctor`: 실패 기록, 색인 준비 상태, 임베딩 모델 파일, MCP 등록을 읽고 문제마다 고치는 명령 한 줄을 낸다. 아무것도 바꾸지 않는다.

#### 4.4.2 색인 전에도 키워드 검색이 된다

- 설치 뒤 첫 세션 시작의 따라잡기 색인이 두 단계로 돈다.
  1. `--no-vector` 색인: 메타데이터, 키워드, 그래프
  2. 벡터 색인
- 1단계가 끝나면 검색은 키워드 결과와 `vector_unavailable`, `degraded_keyword_only` 경고를 낸다. 첫 색인에는 벡터 저장소가 아직 없어서 `vector_stale`이 아니라 이 경고가 나온다(`retrieval_service.py:414-426`). 모델 교체 때(`README.md:236-249`)는 저장소가 이미 있어서 `vector_stale`이 나온다.
- 1단계 시간은 재지 않았다. 구현 전에 Vault 6개로 잰다.

## 5. Decisions

1. 결정1 [사용자, 2026-11-11] 색인 실패 표시(S1)를 진행한다.
2. 결정2 [사용자, 2026-11-11] 검색 품질 평가는 CI가 아니라 로컬에서 돌린다.
3. 결정3 [사용자, 2026-11-11] 이 spec의 범위는 검색 품질과 기억 품질이다. 색인 전 검색과 기억 정리를 포함한다.
4. 결정4 [사용자 승인, 2026-11-11] 평가를 먼저 만들고 개선을 나중에 한다. 이유: 발견3. 지금 질문 수로는 개선 효과를 판정할 수 없다.
5. 결정5 [사용자 승인, 2026-11-11] 층1이 주 지표이고 층3(LongMemEval)은 보조다. 이유: 층3은 영어 일상 대화이고 wiki와 한국어를 재지 않는다.
6. 결정6 [사용자 승인, 2026-11-11] 질의 확장과 페이지 보강은 호출하는 에이전트가 한다. 이유: 도구 안 LLM 금지 원칙을 지키면서 같은 효과를 낸다.
7. 결정7 [사용자 승인, 2026-11-11] 재순위 모델은 손실 분류표의 조건을 만족할 때만 넣는다. 이유: 모델 내려받기와 검색 시간이 늘고, 후보 손실에는 효과가 없다.
8. 결정8 [사용자 확정, 2026-11-11] 2.1의 목표 숫자를 S3 기준값으로 정했다. 목표11(층2 회귀 하한)을 더했다.
9. 결정9 [사용자, 2026-11-11] 층2 가상 Vault는 새로 지어낸다. 실제 Vault를 가공하지 않는다.
10. 결정10 [사용자, 2026-11-11] LongMemEval은 20문항으로 시간을 잰 뒤 범위를 정한다. 전체가 2시간 안이면 470문항 전체로 한다.
11. 결정11 [사용자, 2026-11-11] summary와 aliases만으로 S7을 먼저 한다. "답하는 질문" 필드는 측정 뒤 vault-builder에 요청할지 정한다.
12. 결정12 [사용자, 2026-11-11] 기억 정리를 일정에 따라 자동으로 돌리지 않는다. 알림만 강하게 한다(4.3.3).
13. 결정13 [사용자, 2026-11-11] 에이전트가 던진 검색 질의를 Graph Home `usage/`에 기록한다.
14. 결정14 [사용자, 2026-11-12] 기본 검색 모드는 Vault의 `docs/`를 보지 않는다. 층1에서 `docs/`만 정답인 17문항을 뺀다. 이유: `docs/`는 Vault 운영 규칙과 틀 문서라 wiki 내용 검색에 쓸모가 적다. 넣어 잰 결과 wiki 질문 7문항이 나빠졌다(보고서 3.1).
15. 결정15 [사용자, 2026-11-12] 검색 시간(4.2.6)을 S5보다 먼저 고친다. 이유: 층1 한 번 재는 데 2시간이 걸려 S5~S10에서 방안을 비교할 수 없다.
16. 결정16 [사용자 위임, 2026-11-12] 방안A(S6)를 먼저 진행한다. 지식 검색은 한국어 원문과 영어 표현을 함께 넣고, 세션 검색에는 영어 표현을 권하지 않는다. 이유: 실패의 원인 1위가 한국어 페이지 쏠림이고, 시뮬레이션에서 방안A가 가장 크게 올렸다(손실 보고서 `docs/design/reports/2026-11-search-loss-classification.md` 3).
17. 결정17 [사용자 위임, 2026-11-12] 같은 Vault 안 세션 교환 사본 접기와 대체된 페이지를 근거로 붙이기를 S13(작업 25)으로 더한다. 이유: 손실 보고서 발견2, 발견3.
18. 결정18 [사용자 위임, 2026-11-12] 방안C(작업 21)는 S6과 S13 뒤 층1을 다시 재서 판정한다. 남은 실패가 주로 6~30위 순위 손실이고 재정렬을 넣은 p95가 1초 이하일 때만 넣는다.
19. 결정19 [사용자 위임, 2026-11-12] 방안D(작업 22)는 건너뛴다. 방안B는 S7 보강 뒤 작업 16에서 잰다. 임베딩 교체 spec은 열지 않는다. 이유: RRF 조정은 ±3문항으로 잡음 수준이고, Kiwi는 근거가 없고, 후보 손실이 28%로 4.2.5 조건에 못 미친다.

## 6. Failure and boundary behavior

- 평가 도구는 실제 Graph Home을 바꾸지 않는다. 복사본이나 새 Graph Home에서 돈다. 측정이 사용 기록을 남기지 않게 한다.
- 층1 질문과 문항별 결과는 저장소 안 경로에 쓰지 못한다(기존 `_require_outside_repository` 규칙 유지).
- 층3 변환기는 임시 Vault만 쓴다. 등록된 Vault를 대상으로 받으면 거절한다.
- `queries`가 비었거나 4개를 넘으면 오류를 낸다. 표현 하나가 실패하면 나머지로 답하고 경고를 넣는다.
- Vault 도구가 새 frontmatter 필드를 거절하면 `remember`는 그 필드 없이 다시 시도하지 않는다. 거절 이유를 그대로 돌려준다.
- 재순위 모델 파일이 없거나 읽기에 실패하면 재순위 없이 답하고 경고를 넣는다.
- `vg doctor`는 읽기만 한다. Vault와 Graph Home을 바꾸지 않는다.
- 검색 질의 기록은 Graph Home `usage/`에만 남는다. 세션 가림 규칙(`operation/sessions/redact.py`)을 질의 문자열에도 적용한다.
